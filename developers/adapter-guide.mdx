# Adapter guide

This page is for developers writing a new adapter contract — typically because the target protocol pays reward tokens through a non-standard distributor. If the target protocol is a clean ERC-4626 vault with no rewards, you do not need a new adapter; the existing `GenericERC4626Strategy` handles it. See [Add a new protocol](/integrations-add-new-protocol) for the operational checklist in that case.

## When you need a new adapter

| Target protocol shape | Adapter |
|---|---|
| ERC-4626, no rewards | `GenericERC4626Strategy` (existing — no new code) |
| ERC-4626 + rewards via Merkle distributor (Morpho-like) | New contract extending `GenericERC4626Strategy`, override `handleClaimExtraReward` |
| ERC-4626 + rewards via streaming/escrow contract | New contract extending `GenericERC4626Strategy`, override `handleClaimExtraReward` |
| Non-ERC-4626 (custom deposit/redeem ABI) | New contract extending `BaseAdapter`, implement all four `IFarmProtocolHandler` methods |

The first row needs zero engineering effort. The middle two are the common adapter authoring case. The last is rare and the highest engineering risk — verify the protocol does not have an ERC-4626 wrapper before going down that path.

## Interface

Every adapter implements `IFarmProtocolHandler`:

```solidity
interface IFarmProtocolHandler {
    function handleDeposit(address vault, address token, uint256 amount) external returns (uint256 shares);
    function handleWithdraw(address vault, address token, uint256 shares) external returns (uint256 assets);
    function convertToAssets(address vault, uint256 shares) external view returns (uint256);
    function handleClaimExtraReward(
        address urd,
        address rewardToken,
        uint256 claimableAmount,
        bytes32[] calldata proof
    ) external returns (uint256 claimedAmount);
}
```

All mutating methods are gated by `onlyStrategyManager`. `BaseAdapter` provides the modifier and a default `handleClaimExtraReward` that reverts with `NotImplemented`.

## Pattern: extend `GenericERC4626Strategy`

For ERC-4626 + rewards, inherit from `GenericERC4626Strategy` and override only `handleClaimExtraReward`. `MorphoStrategy` is the reference example:

```solidity
contract MorphoStrategy is GenericERC4626Strategy {
    function handleClaimExtraReward(
        address urd,
        address rewardToken,
        uint256 claimableAmount,
        bytes32[] calldata proof
    ) external override onlyStrategyManager returns (uint256 claimedAmount) {
        // Snapshot before-balance to compute actual claimed amount
        uint256 balanceBefore = IERC20(rewardToken).balanceOf(strategyManager());

        IUniversalRewardsDistributor(urd).claim(
            strategyManager(),
            rewardToken,
            claimableAmount,
            proof
        );

        uint256 balanceAfter = IERC20(rewardToken).balanceOf(strategyManager());
        claimedAmount = balanceAfter - balanceBefore;
    }
}
```

The pattern:

1. Snapshot the StrategyManager's reward-token balance before the claim.
2. Call the protocol's distributor with `recipient = strategyManager` so the tokens land directly in the StrategyManager.
3. Compute the actual `claimedAmount` from the balance delta — never trust the input `claimableAmount` blindly.

## Storage and upgrade pattern

Adapters are upgradeable via UUPS, with namespaced storage following ERC-7201:

```solidity
/// @custom:storage-location erc7201:tumbuh.<adapterName>.storage
struct AdapterStorage {
    address strategyManager;
    // append-only: add fields at the end on upgrades
}
```

Use the same naming convention as the existing adapters (`tumbuh.morphoStrategy.storage`, `tumbuh.genericERC4626Strategy.storage`). The slot is computed once and stored as a constant. See `src/adapters/BaseAdapter.sol` for the boilerplate.

## Authoring checklist

<Steps>
  <Step title="Inherit from the right base">
    Most cases: `contract MyStrategy is GenericERC4626Strategy`. Pure-custom (non-ERC-4626) cases: inherit from `BaseAdapter` directly and implement all four interface methods.
  </Step>

  <Step title="Implement the protocol-specific method">
    For reward claiming, override `handleClaimExtraReward`. The signature is fixed at the interface — adapt the body to call your protocol's distributor.

    For non-ERC-4626, also implement `handleDeposit`, `handleWithdraw`, and `convertToAssets`. The deposit and withdraw methods must:

    - Pull tokens from the StrategyManager at the start.
    - Push tokens back to the StrategyManager at the end.
    - Hold no idle balance between calls.
  </Step>

  <Step title="Initialize the storage">
    Implement `initialize(address _strategyManager, address _owner)` to set the StrategyManager pointer and the upgrade-authority owner. Use OpenZeppelin's `Initializable` + `UUPSUpgradeable` pattern.
  </Step>

  <Step title="Test against a real external vault">
    Tumbuh's test suite uses Foundry forking to test against the real Base mainnet vaults. Add tests under `test/` that fork Base, deposit through the StrategyManager, withdraw, and verify accounting. See the existing `test/Integration.t.sol` patterns.
  </Step>

  <Step title="Deploy with ERC1967Proxy">
    Adapter proxies use the OpenZeppelin `ERC1967Proxy` — not the custom UUPS proxies under `src/proxy/`. The deployment pattern is:

    ```solidity
    MyStrategy impl = new MyStrategy();
    bytes memory data = abi.encodeCall(MyStrategy.initialize, (strategyManagerAddr, ownerAddr));
    ERC1967Proxy proxy = new ERC1967Proxy(address(impl), data);
    ```

    The deployed proxy address is what you register with `addFarmStrategy`.
  </Step>

  <Step title="Register with StrategyManager">
    The Operator calls `strategyManager.addFarmStrategy(proxy, vault, percentage)`. See [Add a new protocol](/integrations-add-new-protocol) for the operational checklist.
  </Step>
</Steps>

## Common pitfalls

| Pitfall | Why it matters |
|---|---|
| Holding token balances in the adapter between calls | Adapters are not vaults. Funds left in the adapter are not counted by `convertToAssets` and may be lost on upgrade. Always push to the StrategyManager at the end of each call. |
| Trusting the caller's `claimableAmount` for `handleClaimExtraReward` | The input is hint-only. Always compute the actual claimed amount from a balance delta. |
| Forgetting `onlyStrategyManager` on a mutating method | Public mutating methods are a security hole. Inherit from `BaseAdapter` and use the modifier. |
| Reverting in `convertToAssets` | The Vault's `totalAssets()` falls back to `lastKnownValue` if `convertToAssets` reverts — but a chronically-reverting adapter freezes its TVL contribution at the last successful value. Test that view-only paths never revert under normal conditions. |
| Non-monotonic storage layout on upgrade | ERC-7201 keeps namespaces separate, but you still must append fields to your `Storage` struct, never reorder or remove them. |
